# 飞书落地规则（作业 2 试作版）

## 各入口的职责

- Codex Skill 处理访谈并生成可校验的本地 bundle。飞书聊天中的 Codex 机器人可以发起同一个 Skill，但必须确认它使用正确的项目目录、能够访问原始材料，并且是在受访谈资料使用范围允许的会话中。
- 飞书多维表格存审阅状态及团队共同维护的记录。飞书聊天只用于发起处理、返回结果链接与讨论，不作为证据库。
- 飞书连接器或 `lark-cli base` 负责读取和写入多维表格。它与聊天机器人是两种入口，不是两套独立的洞察算法。

## 表结构

一个 Base，四张表。每张表都保存 `项目ID` 和本层稳定 ID，以二者作为跨项目查重键；不要用平台记录 ID 替代研究 ID。飞书关联字段仍需使用平台 `record_id`。

1. `访谈来源`：`访谈ID`（主字段）、`项目ID`、`研究问题`、`问题版本`、`受访者匿名编号`、`日期`、`方法`、`情境`、`原文件`、`原文件URL`、`转录版本`、`使用范围`、`资料性质`。
2. `原始片段`：`片段ID`（主字段）、`项目ID`、`访谈ID`、`关联访谈`、`说话人`、`原话`、`相邻提问`、`起始行`、`结束行`、`来源定位`。原话与行号必须能在原文件逐字核对。
3. `原子观察`：`观察ID`（主字段）、`项目ID`、`片段ID`、`关联片段`、`证据类型`、`任务`、`动作`、`对象`、`情境`、`阻碍`、`直接后果`、`应对办法`、`未知信息`。一条观察只表达一个可追溯事实。
4. `候选洞察`：`洞察ID`（主字段）、`项目ID`、`候选问题陈述`、`适用用户与场景`、`支持观察ID`、`关联支持观察`、`相反或限定观察ID`、`关联限定观察`、`支持原话与定位`、`限定原话与定位`、`其他可能解释`、`待验证问题`、`审议状态`、`审议人`、`审议理由`。后两个原话字段是便于逐卡审阅的快照，正式证据路径仍是关联记录与原始文件。

`候选洞察` 建“待审”表格视图，筛选审议状态为 `待审`；可另建按状态分栏的看板视图，供小组集中审议。不要为了展示而额外做独立网页。

## 导入与更新

1. 先运行 `cards.py validate`；演示数据必须标明 `DEMO` 和“模拟”，不能与真实访谈混用。
2. 按 `访谈来源 → 原始片段 → 原子观察 → 候选洞察` 导入。关联字段须用目标记录的飞书 `record_id`，不能直接填稳定 ID。`05_审阅卡片_快速导入.csv` 仅用于没有四表库时的单表快速演示，不要与第四张表重复导入。
3. `scripts/publish_feishu.py` 发布前按 `项目ID + 稳定 ID` 查重。新记录创建；已有记录全部跳过，避免覆盖审议与设计师修改。若同一 ID 的原文或分析发生变化，需要明确版本与人工复核，当前脚本不会悄悄覆盖。
4. 需要回读人工审议、更新已有记录、保持双向同步或自动生成需求时，先扩展工具并单独验证；当前脚本尚不支持。

## 权限

优先以用户身份创建 Base，确保创建者本人可见；若用户授权过期，应刷新授权，而不是静默改用 bot 身份。真实访谈须先匿名化，再按资料使用范围设定 Base、原文件和机器人会话的访问权限。
